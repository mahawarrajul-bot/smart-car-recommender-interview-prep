1. Two-minute pitch

Problem. The spec says buyers face 100+ models, spend 10+ hours researching with no clear prioritisation, and overlook environmental impact. (That figure is the spec's own claim, not something I measured.)

Users. A car buyer with a budget of $10,000–$50,000 who states a location, a vehicle type, a primary use, and optionally a minimum reliability and a maximum CO₂ per mile.

What it does. It filters a 50-car catalog, scores each remaining car 0–100 on five dimensions (budget fit, 5-year total cost of ownership, emissions, reliability, resale), and returns the top 5 with a plain-English explanation and an itemised cost breakdown.

What makes it stand out. The ranking is transparent and reproducible: fixed weights, documented formulas, deterministic tie-breaks, and regional insurance and electricity costs feed the TCO. Cost and emissions sit side by side, not just sticker price.

2. Architecture and request flow

A single Next.js app: a React client form, one API route, and a pure TypeScript engine. There is no database, no auth, and no external service call.

3. How each module works

lib/engine/scorer.tsFive 0–100 scores + weighted totalWeights 25/25/20/20/10. TCO score is anchored to 2× the user's budget, not to the other candidates.
lib/engine/ranker.tsFilter, score, sort, explainHard filters: price ≤ 1.2×budget, reliability ≥ min, CO₂ ≤ max. Then a soft type/use preference sorts first; ties by total, lower TCO, then id.
lib/engine/constants.tsAll spec numbers in one placeMakes assumptions easy to find and change.
app/api/recommend/route.tsHTTP layer400 VALIDATION_ERROR, 404 NO_MATCHES, 500 INTERNAL_ERROR (details logged, not returned). Adds meta with timing and counts.
components/RecommendationForm.tsx, ResultsCard.tsx, app/page.tsxUIClient components; the form calls fetch('/api/recommend').

The scoring formulas

budgetFit = 100 if price ≤ budget else budget/price × 100   (0 beyond 120%)
tco       = max(0, 100 − TCO / (2 × budget) × 100)
emissions = 100 if <150 g/mi; 100 − (CO₂−150)/150 × 80 up to 300; 20 above
reliability = vehicle score as-is      resale = 5-yr retained % as-is
total = .25·budgetFit + .25·tco + .20·emissions + .20·reliability + .10·resale

Soft preference ordering

Type fit (electric = 1; hybrid counts 0.5 for an "electric" request; otherwise body type match) plus use fit (luxury, off-road, family) is summed. Cars with a higher preference sum sort ahead of cars with a higher total score. So a better-matching, lower-scored car can outrank a higher-scored non-match. This is deliberate, and I should say so before being asked.

7. Results and evaluation

What the results show
  • Spec Example 1 (CA, $40k EV): Tesla Model 3 ranks #1; scores 100/64/100/88/65, total 85; TCO $28,996 (fuel $3,086, insurance $7,410, maintenance $4,500, resale $26,000).
  • Spec Example 2 (TX, $25k SUV): Honda CR-V ranks #1, all five are SUVs, all ≤ $30,000, TCO within $500 of the spec's ~$28,500.
  • Spec Example 3 (a $15k luxury EV, 90+ reliability, ≤100 g/mi) returns no recommendations (404 NO_MATCHES in the API).
  • Case 4.2: a $25k sedan buyer gets a Corolla or Civic first. Case 4.3: a $50k luxury buyer sees four luxury sedans first, led by the Lexus ES 300h.
  • README's sample response shows processTime: 25 ms and 12 candidates of 50 for Example 1.
What the results do NOT show
  • Real-world accuracy. Prices, resale %, reliability and CO₂ are rounded estimates calibrated to the spec examples, not manufacturer, EPA or Consumer Reports data. The catalog was shaped so the spec's expected answers come out.
  • User value. No user study, no comparison against other recommenders, no ground truth for "best car".
  • Performance. One logged 25 ms sample is not a benchmark. The spec's "< 1 second" criterion was not measured under load.
  • Deployment. The spec checklist says "Deployed to Vercel", but nothing in the repo records a live URL. I haven't verified one.
  • Weights. 25/25/20/20/10 come from the spec, with no sensitivity analysis or tuning.

8. Limitations, trade-offs, next steps

  • Estimated data, hardcoded: 50 cars (9 electric, 10 hybrid, 31 gas, 0 diesel; 22 sedan, 24 SUV, 4 truck; 6 luxury). Diesel is supported in code but has no catalog entries.
  • Hybrid penalty. The spec's 0.6 factor costs hybrids as less efficient than the same car on gas. This is a modelling choice I'd flag as questionable.
  • No lower budget bound. A $50k budget includes cheap cars; they score 100 on budget fit.
  • No-match zones. The cheapest car is $17,500, so budgets under about $14,600 return nothing; strict filter combinations can too.
  • Coarse regions. Only CA, TX, NY have their own values; other locations use the national default. Gas is a fixed $3.50 and mileage a fixed 12,000/year.
  • Preference ordering can put a lower-scoring match ahead of a higher-scoring non-match.
  • Stateless. No accounts, saved searches or analytics. Invalid locations silently fall back to DEFAULT.
  • Next steps (my proposals): real data source behind a database (spec v2), CI on push, UI tests, user-adjustable weights, fuel-price and mileage inputs, more states, sensitivity analysis of the weights.

10. Glossary

TCO
Total cost of ownership over 5 years: purchase + fuel + insurance + maintenance − resale.
Budget fit
0–100 score for how close the price is to the budget; 100 at or under budget.
Soft vs hard filter
Hard filters remove cars; soft preferences only reorder them.
g/mile CO₂
Grams of CO₂ per mile; here a spec-calibrated estimate, not an EPA figure.
Resale value (5 yr)
Percentage of purchase price retained after 5 years.
App Router / route handler
Next.js file-based routing; route.ts exports an HTTP method function.
Vitest
The JavaScript test runner used here.
Deterministic
Same input gives the same output; the tie-break chain ensures it.
Spec-driven development
Writing a detailed specification first, then implementing and testing against it.
Sensitivity analysis
Checking how results change when weights or assumptions change (not done here).
